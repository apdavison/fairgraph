============================
Maintenance and operations
============================

This page describes procedures carried out by the fairgraph maintainers,
in addition to those in :doc:`contributing`.


Updating the EBRAINS Software Distribution
==========================================

fairgraph is included in the EBRAINS Software Distribution (ESD), as the Spack package ``py-fairgraph``
in the `ebrains-spack-builds`_ repository. After each release, once it is on PyPI
(see :ref:`making-a-release`), add the new version there:

1. In a fork of ebrains-spack-builds, edit :file:`packages/py-fairgraph/package.py`:

   - add a ``version()`` line for the new release above the existing ones, giving the sha256 checksum
     of the source distribution on PyPI;
   - bring the ``depends_on()`` lines into line with the dependencies in :file:`pyproject.toml`.
     Where a minimum version has changed, add a new ``depends_on()`` line with ``when="@<version>:"``,
     and limit the existing line to earlier versions, rather than changing it, so that older fairgraph
     versions keep their own constraints.

2. In the top-level :file:`spack.yaml`, update the version of ``py-fairgraph``.

3. Open a merge request against the upstream repository.


The mirror on EBRAINS GitLab
============================

The canonical fairgraph repository is on GitHub. A copy is kept on the EBRAINS GitLab,
at https://gitlab.ebrains.eu/data-services/fairgraph, by the GitHub Actions workflow
:file:`.github/workflows/ebrains.yml`. On every push to ``master``, the workflow copies ``master``
to the GitLab ``main`` branch, and copies all tags.

The workflow pushes with ``--force``, so the GitLab repository always matches GitHub, and any change
made directly on GitLab is overwritten by the next push to ``master``. Mirroring in the other direction,
from GitLab to GitHub, would be impractical, and is not planned: all changes should be made through GitHub.

The workflow authenticates with a GitLab *project access token* on the GitLab project, stored in the
GitHub repository secret ``EBRAINS_GITLAB_ACCESS_TOKEN``. It needs the ``write_repository`` scope, and a role
that is allowed to push to ``main``. Project access tokens expire, after which the workflow fails
with an authentication error. To renew it:

1. In the GitLab project, under :menuselection:`Settings --> Access tokens`, create a new project access token
   with the ``write_repository`` scope (this requires the Maintainer role in the project).
2. In the GitHub repository, under :menuselection:`Settings --> Secrets and variables --> Actions`,
   replace the value of ``EBRAINS_GITLAB_ACCESS_TOKEN`` with the new token
   (this requires admin rights on the repository).
3. Re-run the most recent run of the workflow, from the :menuselection:`Actions` tab on GitHub.


Credentials for the tests
=========================

The tests that run against the Knowledge Graph need an EBRAINS authentication token in the environment
variable :envvar:`KG_AUTH_TOKEN`, and are skipped without one (see :ref:`running-tests`).
Use a token for a normal user account (ideally a test user), which does not have curator permissions.
They run against the pre-production KG, never production.

Checking the release status of an instance requires curator permissions in the KG,
so the test of :meth:`KGClient.is_released` uses a second token, for an account with those permissions,
in the environment variable :envvar:`KG_AUTH_TOKEN_CURATOR`. It is skipped if that variable is not set.

The continuous integration workflow does not set either variable, so these tests are
skipped there, and run only when a developer runs the test suite locally with a token.


Generated files
===============

Two files are generated from metadata kept in :file:`doc/`, and should not be edited by hand:

:file:`codemeta.json`
    Generated by :file:`doc/build_codemeta.py` from :file:`pyproject.toml`, :file:`doc/authors.json`
    and :file:`doc/organizations.json`. It describes the most recent release, so it is regenerated
    only when making a release (see :ref:`making-a-release`).

:file:`doc/authors.rst`
    Generated by :file:`doc/build_authors.py` from :file:`doc/authors.json`, using the template
    :file:`doc/authors.rst.tpl`. Affiliations are looked up in the `ROR`_ registry, and the results cached
    in :file:`doc/.rorid_cache` (delete this file to refresh them). After editing :file:`doc/authors.json`,
    regenerate it with::

        $ cd doc
        $ python build_authors.py

    The documentation's :file:`Makefile` runs this script only if :file:`doc/authors.rst` does not exist.

.. _ROR: https://ror.org
